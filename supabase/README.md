# Backend (Supabase)

The optional cloud side of UAV Companion. The app works fully without it (everything stays in the browser); this folder holds what a signed-in user's cloud copy needs. Nothing here is loaded unless a project address is configured (see `.env.development.local` below).

## What is here
- `migrations/`: the database as SQL, applied in file-name order. The same files run on a local database, in the tests and on the hosted project.
  - `20261111120000_user_data.sql`: one document per user (markers, trips, a few settings) with a revision number, the previous versions kept for 30 days (at most 20), row-level security, and the functions that are the only way to write (`save_user_data`, `list_user_data_versions`, `restore_user_data_version`, `delete_user_data`).
  - `20261111130000_friends.sql`: profiles (display name, friend code), friendships (request, accepted) and blocks, with the functions that are the only way in (`ensure_profile`, `set_accepts_requests`, `regenerate_friend_code`, `request_friend`, `respond_friend`, `remove_friendship`, `list_friends`, `block_user`, `list_blocked`, `unblock`, `delete_profile`). Tested in `tests/db-friends-unit.mjs`.
  - `20261111140000_shared_trips.sql`: shared trips (one document per trip with a revision), their members (owner, invited, party members), earlier versions kept 30 days (at most 20), and the functions that are the only way in (`share_trip`, `invite_to_trip`, `list_invitable_friends`, `respond_trip_invite`, `leave_trip`, `remove_member`, `delete_shared_trip`, `list_my_trips`, `list_trip_members`, `get_shared_trip`, `save_shared_trip`, `list_shared_trip_versions`, `restore_shared_trip_version`). Tested in `tests/db-trips-unit.mjs`.
  - `20261111150000_presence.sql`: online status (`touch_presence`, `set_show_online`, and the status columns of `list_friends` and `list_trip_members`). Tested in `tests/db-presence-unit.mjs`.
  - `20261111160000_live_locations.sql`: the latest position of each party member who is sharing (`live_locations`, one row per person and trip, no history), and `share_location`, `stop_sharing_location`, `stop_all_sharing`, `list_live_locations`; leaving or removal deletes the position. Tested in `tests/db-live-unit.mjs`.
  - `20261112100000_live_device.sql`: a `device` on each position; the device that starts sharing takes the position over, an older one is told `moved`. Tested in `tests/db-live-unit.mjs` and `tests/live-engine-unit.mjs`.
  - `20261113110000_profile_named.sql`: `profiles.named` (false for a new profile, true for existing ones and once a name is given or changed), returned by `ensure_profile`; `choose_name(text)` for the first-sign-in question (a name, or null to keep the default). Tested in `tests/db-profile-unit.mjs`.
  - `20261112110000_profile.sql`: `avatar` (a key of a fixed list), `bio` (160), `location` (60, typed), `interests` (up to 5 keys of a fixed list) and `share_profile` on `profiles`; `update_profile(jsonb)`; the new fields in `ensure_profile`, `list_friends`, `list_trip_members`; the editor's avatar in `list_shared_trip_versions`. Lists: `profile_avatars()`, `profile_interests()`.
  - `20261113100000_delete_account.sql`: `delete_profile` now also hands trips on and removes positions and trip places; `delete_account` adds the cloud copy and its versions; the internal `leave_all_trips`. A trip the caller owns goes to the member who joined first, or is deleted when nobody else joined.
  - `20261114100000_progression_core.sql`: progression phase 1. The append-only XP ledger (`xp_ledger`, unique on user + source + ref so an award cannot be recorded twice), each person's running total and peak tier (`user_xp`, kept by a trigger), the rank ladder and earning rates as data (`progression_ranks`, `progression_settings`), `rank_for(xp)` (rank is never stored), roles (`app_roles`: admin, organiser) and the functions `my_roles`, `grant_role`, `revoke_role`, `admin_adjust_xp` (reason required, floor at 0, own XP refused), `admin_verify_xp`. The only XP inserter, `award_xp`, is internal. Tested in `tests/db-progression-unit.mjs`. Deleting a profile (`delete_profile`) leaves XP alone; deleting the account removes it. **First administrator:** after applying the migration, the project owner runs once, in the SQL editor or `npx supabase db query --remote`: `insert into public.app_roles (user_id, role) values ('<auth user id>', 'admin');` (never put the id in a migration).
  - `20261114110000_achievements.sql`: progression phase 2. Achievement definitions as data (`achievements`: key, category, name, description, rarity, icon, one metric and threshold, optional season window), the 16 launch rows, permanent unlocks (`user_achievements`, never changed or removed, first unlock time kept), the featured three (`featured_achievements`, only unlocked ones), monotonic counters (`user_counters`, used for shared trips created) and the internal engine (`user_metric`, `evaluate_achievements`, `bump_counter`). `award_xp` now runs the engine in its own transaction, and a trigger on `shared_trips` counts each creation. The only user-callable function is `set_featured`. Also fixes the phase 1 ledger guard so deleting an administrator's account no longer fails (the actor of their adjustments becomes null, nothing else changes). Existing shared-trip owners get Planner with their first trip's creation time. `First Connection` stays locked until the Steam phase; real-world flying achievements are not defined. Tested in `tests/db-progression-unit.mjs`.
  - `20261114120000_progression_read.sql`: progression phase 3. `get_progression(kind, id)`, `list_progression(kind, ids)` (at most 100), `my_progression()` and `my_xp_history(before, limit)`. A person is named by a friendship id (`'friend'`) or a party member id (`'member'`), never a user id; the internal `progression_viewable` allows it only for an accepted friend or a joined member of a trip the caller has joined, with `share_profile` on and no block in either direction, and every other case gives the same `{visible: false}`. Others see rank, exact XP, progress, the featured three and each achievement's unlocked flag (no times); only the owner sees unlock times and an XP history (reasons only for administrator adjustments; never an actor or reference). `list_friends`, `list_trip_members` and `list_live_locations` are unchanged. Tested in `tests/db-progression-read-unit.mjs`.
  - `20261114130000_flight_sessions.sql`: progression phase 5. `flight_sessions`, `session_rsvps` (no XP) and `session_attendance` (who verified, when, revoked or not); `create_session`, `update_session`, `close_session`, `cancel_session`, `list_sessions` (a count of RSVPs, never who), `rsvp_session`, `withdraw_rsvp` (before the start only), `list_session_rsvps` (managers only, no user ids), `mark_attended` (by RSVP handle or friend code; from the start until closed; never yourself; XP once per person per session through the ledger), `revoke_attendance` (administrators, reason required, appends a ledger reversal, keeps the row and achievements). An organiser manages the sessions they created; an administrator all. `award_xp` also allows the `session:<id>:rev` reversal; `delete_profile` also withdraws RSVPs. Tested in `tests/db-sessions-unit.mjs`.
  - `20261116100000_steam_existing_hours.sql`: Steam credits hours played before linking. `steam_link` no longer takes a baseline: it applies the approved games' totals through `apply_steam_playtime` (10 XP per completed hour, at most 500 hours per sync). `unlink_steam` keeps the stored per-game totals; new column `steam_links.state_steam_id` records which Steam account they belong to, so relinking the same account credits only new play. New table `steam_credited` (Steam id, game, highest total ever counted; no access for the app, never deleted) is the baseline for a person linking a Steam account they have not had before, so a Steam account's history pays out once, whoever links it. For existing links the stored totals stay (and are copied into `steam_credited`), except for people who had earned nothing yet (theirs are removed, so their next sync credits everything). Tested in `tests/db-steam-unit.mjs`.
  - `20261114140000_steam.sql`: progression phase 6. The approved simulators (`steam_apps`: Liftoff®: FPV Drone Racing 410340, Liftoff®: Micro Drones 1432320, FPV LOGIC 2398030, Uncrashed 1682970, The Drone Racing League Simulator 641780, TRYP FPV 1881200), `steam_links` (per person: Steam id, counters, last status, manual-sync stamp; kept when unlinking), `steam_app_state` (last total per game). Service-role-only functions: `steam_link` (links; from `20261116100000` it credits the existing playtime once per Steam account; First Connection), `apply_steam_playtime` (adds max(new total - last total, 0) per approved game, one ledger row `hour:<n>` per completed hour, at most 500 hours per sync, fractions kept), `claim_manual_sync` / `release_manual_sync` (the 60 minute cooldown, claimed atomically and given back when Steam fails), `list_steam_due` (linked people last synced over 20 hours ago). For the app: `my_steam()` (never the Steam id), `unlink_steam()`, `list_steam_apps()`. `steam_enabled` (a setting, 0) switches it on. Tested in `tests/db-steam-unit.mjs`.
  - `20261115100000_efficiency.sql`: efficiency review. `shared_trips.start_date` / `end_date` columns (filled from the document, kept by `share_trip` and `save_shared_trip`) so `list_my_trips` and `share_location` no longer read the whole document; `list_my_trips` gains `live_active` (other members sharing their location now); the position clean-up in `share_location` runs only when old rows exist; indexes on `live_locations(updated_at)`, `steam_links(last_synced_at)`, `session_rsvps(user_id)`, `session_attendance(user_id)` and the foreign keys followed on account deletion. No policy or grant changes.
  - `20261115110000_version_coalesce.sql`: `save_user_data` and `save_shared_trip` keep the replaced document as an earlier version only if it was not saved by the same device / person less than 2 minutes before (a forced overwrite always keeps it), so a burst of autosaves is one version.
  - `20261115120000_steam_queue.sql`: `apply_steam_playtime` writes the new hours to the ledger in one statement and checks the achievements once (was one `award_xp` and one check per hour); `steam_links.last_attempt_at` is stamped on every attempt and `list_steam_due` orders by it, so people whose sync keeps failing cannot take all 200 places of the daily run. The edge function `steam-sync-all` now works on 5 people at a time and stops starting new ones after 100 s (`left` in its counts).
  - `20261111121000_harden_api_exposure.sql`: takes the API roles' access away from the platform's own `rls_auto_enable()` function.
- `functions/delete-account/`: the edge function that deletes an account (`handler.js` holds the rules and is unit tested; `index.ts` is the Deno entry point). It calls `delete_account` as the user, then removes the `auth.users` row with the service-role key, which the platform supplies to the function as a secret and which is never in the repository or the browser. Deploy: `npx supabase functions deploy delete-account --project-ref <ref>`.
- `functions/steam-link/`, `functions/steam-sync/`, `functions/steam-sync-all/` and `functions/_shared/steam.js`: Steam linking (OpenID sign-in checked with Steam, then the owned games read once and credited, including hours played before linking), a person's own Sync now, and the daily run. `handler.js` files hold the rules and are unit tested (`tests/steam-unit.mjs`); `index.ts` are the Deno entry points. Nothing in the repository holds a key. **To switch it on** (the project owner, once): `npx supabase secrets set STEAM_API_KEY=<your Steam Web API key> STEAM_STATE_SECRET=<a long random string> STEAM_CRON_SECRET=<another long random string> STEAM_RETURN_ORIGINS=https://<your site origin>,http://localhost:5173 --project-ref <ref>`; deploy the three functions (`npx supabase functions deploy steam-link steam-sync steam-sync-all --project-ref <ref>`); then `update public.progression_settings set value = 1 where key = 'steam_enabled';`. **Daily sync**: call `steam-sync-all` once a day with the header `x-cron-secret: <STEAM_CRON_SECRET>`, either from the database (pg_cron with pg_net: `select cron.schedule('steam-daily', '0 3 * * *', $select net.http_post(url := 'https://<ref>.supabase.co/functions/v1/steam-sync-all', headers := jsonb_build_object('x-cron-secret', '<secret>'))$);`, after enabling both extensions) or from a scheduled GitHub Actions workflow that posts to the same address. The daily run has no cooldown; a person's Sync now has one.
- `config.toml`: settings for the local stack (used only if the local stack is ever started).

## Access rules in one paragraph
Row-level security is on for every table. A signed-in user can read their own row and nothing else; the anonymous role has no access at all; **nobody can write to a table directly**. Writes go through the functions, which read the caller from `auth.uid()` and check the size (about 2 MB), the shape and the revision. A save made from an older revision than the server's is refused with `status: "conflict"` and the server's current revision, time, device name and counts, so the app can ask the user which copy to keep. These rules are tested on a real Postgres in `tests/db-unit.mjs`.

## Security advisor: accepted warnings
`supabase db advisors --remote` reports "Signed-in users can execute SECURITY DEFINER function" for every function in the migrations (the cloud-copy ones and the friends ones). That is intended: they are the only write path, each one refuses a caller who is not signed in, none can be executed by the anonymous role, and each touches only the caller's own rows. Any other warning is a finding to look at.

## Working with it
- **Tests (no Docker, no network):** `node tests/db-unit.mjs`. It builds a fresh in-memory Postgres (PGlite), adds the roles and `auth.uid()` that Supabase provides, applies every migration and checks the rules as different users.
- **Apply migrations to the hosted project:** `npx supabase db push --remote --dry-run` shows what would run; `npx supabase db push --remote --yes` applies it. The database password is read from the environment variable `SUPABASE_DB_PASSWORD` (set it once in your Windows account; never put it in a file in this repository).
- **Read-only look at the hosted database:** `npx supabase db query --remote --read-only "select ..."`.
- **Live checks as throwaway users** (they create and delete their own users; need the CLI login): `node tests/cloud-live.mjs` (cloud copy) and `node tests/friends-live.mjs` (friends) and `node tests/trips-live.mjs` (shared trips).
- **Security check:** `npx supabase db advisors --remote`.
- **The link to the project** is stored in `supabase/.temp/` (ignored by git), created by `npx supabase login` and `npx supabase link --project-ref <ref>`.

## What must never be committed
The secret (service-role) key, the database password, the access token. `.env`, `supabase/.env` and `supabase/.temp/` are ignored by git. The project address and the publishable key are public by design and live in `.env.development.local` (read by `npm run dev` only, not by `npm run build` or `npm run deploy`, so the live site does not show sign-in until it is switched on on purpose).

## Environments
The one project created so far is tagged "production" by the platform but is used as the development project while there are no real users. Before real users arrive, create a second project, apply the same migrations there, close public sign-ups, turn email confirmation on, and point the production build at it.
