  - **D5 findings (source reading; not run in a browser):**
    1. **`store.update(id, patch)`** (`poi.js` 335): sanitizes, drops an unknown trip id, `settle`, `stamp` (sets `updated` on an item of a shared trip), saves to localStorage, then `emit()` to every `onChange` listener. It has no permission check and no staging.
    2. **The drag** (`poi-ui.js` 1317 to 1362, edit mode only): while lifted it moves only the Leaflet pin (`m.setLatLng`); nothing is stored. On release it calls `store.update(id, {lat, lon})`, then `mw.invalidate(id)`, `elev.invalidate(id)`, `mw.refresh([id])`, a toast; no Undo.
    3. **What reacts to the `emit()`:** `poi-ui.js` 1466 runs `syncPins()` (collapses any spider fan first, re-evaluates which pins show), `refreshIcons()`, `renderList()`, `wxLine.render()` and `relink()`. `relink()` clears and redraws the Side Quest links, calls `redrawRoutes()`, and redraws the dotted nearest-base distance lines from `store.get` (current stored coordinates). So **routes, distance lines, spidering and the list follow a stored change with no extra call.** Route identity: `routeKey(leg)` is computed from the marker ids and their coordinates (`route/legs.js`, `route/result.js`), so a moved marker gets new keys; old cached rows are simply not matched (`router.js` 22 accepts a stored route only for exactly the leg as it is now). The shared cache `trip_routes` is keyed the same way, written only by the edge function. **No route identity or cache semantics need to change, and none should.** `dashboard.js`, `trips-ui.js` and the sync engines also listen.
    3b. **Weather and elevation** are not listeners: they are invalidated by id (`markerweather.js` `invalidate` deletes the cache entry; `elevation.js` `invalidate` also clears the failed set) and refreshed by the caller. The drag does this by hand, so Save and Undo must do the same.
    3c. **Zone verdict** is computed when the window content is built (`marker-content.js` 137, `checkPoint(it.lat, it.lon)`): reopening the host on the moved marker after Save gives a fresh verdict; nothing is cached on the marker.
    4. **Missing invalidation (gap 1, affects S7):** the Leaflet pin's position is not re-read from the store on a store change. Only the drag calls `m.setLatLng`; `rebuildMarkers()` runs at start-up, on a `storage` event and after import. So after Save (if the pin is not dragged) and after Undo the code must call `m.setLatLng` itself, or the pin stays at the old spot while routes and lines use the new one.
    5. **Possible pre-existing gap 2 (not S7 scope, not verified in a browser):** `store.applyShared` (a collaborator's change arriving by poll) emits `'shared'` and nothing in the listeners repositions pins, so a remote move may not show on the map until a rebuild. Recorded for the owner; S7 must read coordinates from the store, never from the pin, when it decides whether Undo is safe.
    6. **Staged Move can stay entirely in memory:** nothing in `store` or localStorage is touched until Save. Proposed mechanism: a `'move'` mode (not the edit mode, which locks the map) that shows the crosshair at the map centre (as `place` mode does with `map.getCenter()`), live coordinates in a banner, Cancel (also Escape) and Save. The staged value is a local variable; there is no draft to persist (stop condition 12.4). Closing the host or leaving the mode discards it.
    7. **Shared trips, Save:** there is no synchronous revision-checked write at the click. `store.update` changes the local copy; `sharedtrip/engine.js` listens (`onChange`), sees the local document differs from its synced base, marks the trip pending and debounces `push(id)`. `push` calls `api.save(id, doc, rev)`; the database function (`20261111140000_shared_trips.sql`) rejects a stale `p_base_rev` with `status: 'conflict'`; the engine then fetches theirs, runs the three-way `mergeDocs(base, mine, theirs)` (`sharedtrip/core.js`: a field changed on one side only takes that side; **a field changed on both sides takes the record with the later `updated` time**; an edit beats a delete), applies the result locally and retries up to four times. So a Save is local-first and eventually consistent, never lost, and a concurrent move of the same marker is resolved by timestamp.
    8. **Shared trips, Undo, and why D3 is not met by a plain `store.update`:** an Undo is another local change that the engine pushes the same way. If a collaborator moved the same marker in between, the merge would take the Undo (later `updated`) and **silently overwrite their move**; if they deleted it, the merge keeps the marker only if this device changed it, which an Undo would. The backend has no revision-checked single-marker write and S7 may not add one (D1, stop conditions). **Smallest safe design inside the rules:** Undo is offered only for the move it belongs to (kept in memory; gone after reload, another edit of that marker, or the toast timeout); on press it (a) refuses if the marker no longer exists in the store, (b) for a shared trip first runs the engine's `poll()` (serial with pushes, merges anything newer) and then refuses if the stored coordinates are no longer exactly the moved ones or the trip's status is not `synced`, saying "Someone else changed this marker since, so it was not moved back"; (c) otherwise restores the previous coordinates with the same function Save uses. **Residual window, to accept or not:** a collaborator's move saved between that `poll()` and the Undo's own push still resolves by timestamp (Undo wins). Closing it needs a backend change (a base-revision check at Undo), which is out of scope; the same window exists for every ordinary edit today. `poi-ui.js` does not currently hold a reference to the shared engine; it must be passed in (one dependency), not imported across modules.
    9. **Smallest implementation reusing the existing paths:** one `applyMove(id, lat, lon)` in `poi-ui.js` doing exactly the drag's sequence plus `m.setLatLng`: `store.update` (persist, emit and so routes, lines, spider, list, shared sync), `mw.invalidate`, `elev.invalidate`, `mw.refresh`, and a toast with an Undo action for Move. The drag's own code is not touched (D2). No change to `store`, `route/*`, `sharedtrip/*` or any migration.
    10. **Unsafe assumptions to avoid:** treating the pin position as truth; assuming a shared Save is acknowledged by the server when `store.update` returns; assuming an Undo can be a revert of a revision; deleting old cached route rows (not needed and would change cache semantics).

### 9.3 Preferred marker-detail direction (owner, 2026-11-21) as requirements

These are the only prototype layout decisions the owner has stated as preferred. They are **proposed, unapproved** and become binding on approval.

- **MD-01 Host component, not a Leaflet popup.** One adaptive container outside the Leaflet container (as `.ses-explorer` is), `position:fixed`, at `--z-sheet`. It is **non-modal**: no scrim, the map stays visible and operable.
- **MD-02 Folded phones: full-width adaptive bottom sheet.** Edge to edge, safe-area aware, a handle, two states (compact, expanded). Expanded must leave the selected pin visible; the existing phone limit is 60% of the map (`expandedMaxHeight` in `src/view.js`). Prototype sizes of 72% and 92% are not adopted without owner sign-off (U-05).
- **MD-03 Unfolded foldables: wider contextual side panel.** Full height of the free area, `clamp(340px, 47%, 480px)`.
- **MD-04 Desktop: contextual side panel capped near 480 px** (`clamp(420px, 36 to 38%, 480px)`).
- **MD-05 No duplicate titles, no cramped actions.** Name appears once (the heading; the container takes its accessible name from it). Type, trip and day appear once, in one metadata line; chips only for states (Side Quest, Unverified, Outside the trip's dates). Action layout in 9.4 C-10: primary Navigate full width, secondary actions wrap, rare actions in an overflow menu. Minimum 44 px targets, no label clipped at 320 px.
- **MD-06 Choose layout by room, not by device or a hard-coded width.** Side panel when the map container leaves at least 320 px of map beside the panel; otherwise bottom sheet. This is the rule the Sessions explorer already uses (`MAP_MIN`, `layout()` in `src/sessions-map-explorer.js`) and it reproduces P1 to P3 at the prototype widths (side from about 660 px). One shared helper, so the marker panel and the explorer cannot disagree.
- **MD-07 Preserve map visibility and recentre the selected marker in the free area.** Free area = map container minus the marker panel or sheet, minus the open side panel, minus the explorer dock, minus top search row and bottom navigation where present. Selecting a marker (tap, list row, previous / next, search result) pans so the pin sits at the middle of the free area, keeps the zoom, is rotation-aware, and respects a manual pan until the next explicit selection. This logic exists once, in `centerOn` and `visibleRect` of the explorer; extract it, do not write a second copy. The prototype does not demonstrate recentring (its pins are fixed CSS positions).
- **MD-08 Attribution, scale and map controls stay reachable.** *(S1 baseline: attribution is 34 to 50 px tall at the bottom of the map on phones, so a bottom sheet covers it as well as a side panel does.)* A right-hand panel or a bottom sheet would cover the Leaflet attribution (bottom right) and any right-hand map buttons. Offset them with a CSS variable the way the explorer offsets controls with `--ses-x-off`.
- **MD-09 Same content, same rules.** The panel renders everything the current marker window renders (9.5) from one extracted content builder. No simplification of data shown.
- **MD-10 Focus, keyboard, Escape.** Opening moves focus to the heading; closing returns focus to the pin or list row; Escape closes the panel when no dialog is open; edit form inside the panel keeps keyboard-open behaviour on phones (follow `visualViewport` as the sessions hub does).
- **MD-11 Gesture parity.** Swipe-to-dismiss and swipe on the previous / next footer behave as today (`onPopupSwipe`), adapted to the sheet (down) and panel (right). Non-drag alternatives (close button, size toggle) always present.
- **MD-12 Interaction with other overlays.** Opening the Sessions explorer, a point check, the weather card, a dialog or the side panel has a defined precedence (U-04). Defaults: one of marker panel / explorer at a time; point check and weather close the marker panel as they close the popup today.
