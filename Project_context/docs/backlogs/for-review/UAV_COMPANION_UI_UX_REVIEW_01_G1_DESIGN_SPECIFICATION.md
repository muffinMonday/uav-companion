## 13. Method

Each requirement below carries a tag:

- **[F]** — functional requirement carried over unchanged from the current app; the prototype must not regress it.
- **[P]** — adopted from the prototype (a genuinely new direction the prototype proposes and this document recommends accepting).
- **[R]** — **rejected**: the prototype shows this, but it is an invented/illustrative element that must not be built as shown. Reasons given inline.
- **[G]** — a gap: neither the backlog nor the prototype specifies this adequately; a default is proposed and the matching open decision (U-13+) is raised.

Every requirement cites real owning files from `MODULES.md`'s component ownership map (or, where a destination has no component yet, the nearest existing analog) so an implementer is not left inventing file layout. Nothing here introduces a second overlay mechanism: every sheet/dialog/full-screen requirement reuses the marker host's already-built primitives (`src/marker-host.js`'s host pattern, `src/overlay-policy.js`'s precedence policy, `src/free-area.js`'s cut/centre service) generalized to non-marker content, consistent with AM-10's note that B02/B03 must add "the marker-host pattern" as a shared primitive rather than destination-specific code.

Carried-forward rejection list (do not re-propose; backlog section 10.3 and this document's own direct read of the prototype confirm these apply app-wide, not just to markers): the 4-step wizard pattern for anything that is not genuinely complex (D13, U-06); 5-or-fewer invented type/category lists where a real taxonomy exists; "Route to" affordances already removed (U-08); phone sheet heights outside the documented 60%/two-state rule (U-05) without a fresh approval; a scrim behind any non-modal contextual overlay (C-02); search-as-you-type echo or a fabricated "Other regions" chip (C-18); an always-on notification-bell dot with no real pending state (C-17); free diagnostics step navigation or a permanently-disabled Stop control (C-16); Unicode/emoji icons in place of named SVGs (C-20); touch targets under 44px (C-26); dialogs without a focus trap and focus return (C-25); a merged delete/leave-trip dialog (C-29, D14); sizing any fixed/modal overlay from bare `vh` (DESIGN.md's 2026-11-14 dialog-sizing note — Android toolbar reflow; use `%`/`dvh`+`vh` fallback, already the pattern the marker host uses).

## 14. Navigation shell & overlay framework (NAV)

This is the one piece every other destination depends on (backlog section 4: "C01–C04 depend on B; D/E/F/G depend on C"). It did not exist as a workstream in the backlog beyond C01–C04's one-line ACs, and S4–S9 built the marker host directly against the *current* shell without waiting for it (backlog 12.1 footer) — so NAV must be specified now without breaking that already-shipped work.

- **NAV-01 [F/P]** Four primary destinations — Map, Trips, Explore, Profile — per D02/C01. Mobile: bottom navigation (new; today's UI has no bottom nav — `panel.js`'s right-side dock and `dashboard.js`'s floating dashboard are the closest analogs and are superseded here per the supersession register row "Current panel/dock and floating dashboard → Four-destination bottom nav / desktop rail"). Desktop/tablet ≥760px (DESIGN.md's existing compact breakpoint, not the prototype's 690/1000 — see U-03, still open): left navigation rail. **AC:** active/selected state correct; reachable by keyboard (Tab order, Enter/Space activation, visible focus ring at the existing focus-ring token); guest sees all four (D11); every dynamic feature entry point currently reachable from `panel.js`'s dock/tabs or `dashboard.js` is reachable from exactly one of the four destinations or Settings (full mapping: NAV-04 below) — none is dropped.
- **NAV-02 [F]** State preservation (C02): map center/zoom/rotation, selected trip/day, Saved Places list scroll and filters, Explore list scroll/filter and selected session, Profile subview. **AC:** switching destinations and back restores all of the above; signing out/in clears and revalidates private state (matches `src/privacy.js`'s existing session boundary).
- **NAV-03 [P]** Shared overlay precedence (C03/U-04, generalized beyond markers): one non-modal contextual overlay visible at a time across *all* destinations, not just Map; modal dialogs take precedence over any contextual overlay; full-screen views (destination screens, Trips itinerary, Explore session detail, full-screen search) are not "overlays" in this sense — they replace the destination's own content. **AC:** built as one extension of `overlay-policy.js` (already the real, tested policy module) rather than a second implementation; opening a dialog while a contextual overlay (marker panel, route summary sheet, Layers sheet) is open parks it exactly as the Sessions Explorer already parks on a marker-panel open (reuse that proven mechanism, do not reinvent); the marker host's existing precedence behavior (S4–S9) is unchanged by this generalization.
- **NAV-04 [F, decided]** Full entry-point migration map: **U-14 decided 2026-11-22, mapping accepted as proposed.** Every control currently reached via `panel.js`'s dock tabs (`#pane-config`, `#pane-trips`, `#pane-poi`, `#privacy`) and `dashboard.js`'s floating dashboard (task shortcuts, Help subview, More tools, legend/coverage) lands in exactly one of: Map (contextual sheets), Trips, Explore, Profile, Settings, or the Activity inbox. The complete before/after inventory with regression checks is section 28.3 (supersedes the summary table that was here). Motor diagnostics entry stays put (U-13, no relocation to Profile). **AC:** every row of section 28.3 keeps its named regression suite(s) green through the migration (updated in the same change that moves the control, never deleted outright — the S9 test-migration discipline applies here too); no control silently disappears.
- **NAV-05 [G]** There is no "Dashboard" destination in the four-destination model (D02 names only Map/Trips/Explore/Profile). Today's dashboard hosts items with no obvious single new home: Help (`help-ui.js`, `help-content.js`), What's New (`whatsnew.js`), task shortcuts, the mascot greeting, the legend/coverage note. **Default (proposed):** Help and What's New move into Settings "Help & about"; task shortcuts become contextual (shown inside the destination they shortcut to, e.g. a Map task shortcut appears on Map, not centrally); the mascot greeting moves to Profile's hero per G06 below; the legend/coverage note moves to the Layers sheet (it is map configuration, not profile content). **AC:** no shortcut becomes unreachable; mascot placement rules in DESIGN.md section 24 are preserved (compact mascot beside identity, not a redesign of the asset itself, per D10/H1-G in the pasted prompt).
- **NAV-06 [F]** Active-operation navigation guard (C04): prompt before leaving active marker placement/Move, an in-progress trip/session creation wizard-equivalent sheet, or other meaningful unsaved work; the existing, separate, stricter motor-diagnostics navigation guard (`src/benchtest/lifecycle.js`) is untouched — NAV must not introduce a shared guard that could weaken it. **AC:** Cancel from the guard returns to the prior state with no partial mutation (already proven for staged Move, S7; same contract applies here).
- **NAV-07 [F]** Back/browser-history behavior (U-09, generalized beyond the marker panel + full-screen details it names): one history manager backs every full-screen view (Trips itinerary, Explore session detail, full-screen search) and the marker panel; browser Back closes the topmost one before navigating destinations; the diagnostics guard keeps its own, separate history handling per U-09's explicit carve-out. **AC:** a `popstate` round trip on every full-screen view and dialog closes it without navigating away from the app (the prototype's `popstate` handler closes an overlay but never pushes history, per C-15 — real implementation must push on open and pop on close, a correction, not something to copy from the prototype as-is).
- **NAV-08 [R]** The prototype's generic `.sheet`/`.modalbox`/`.fullview` CSS classes are a convenient illustration of three *kinds* of overlay (confirmed by direct prototype read: `overlayContent(n)` is one switchboard emitting all three), matching the already-accepted C-02/C-03 narrow decision for markers (three kinds: non-modal contextual, modal dialog, full-screen). This pattern is adopted at the *conceptual* level only (NAV-03); the prototype's actual CSS/markup for these three kinds was never corrected for non-marker content the way the marker sheet's sizing was (confirmed: only a `.marker-detail-sheet` override block was retrofitted into the prototype's `<style>`, nothing else was). **Do not copy the prototype's non-marker sheet/dialog/full-view CSS or layout as if it were reconciled** — only the marker ones (MD-02 to MD-04) are. Non-marker sheets, dialogs and full-screen views need their own sizing pass against DESIGN.md section 9's real breakpoints once U-03 is resolved.
- **NAV-09 [F, decided]** **U-03 decided 2026-11-22 (option C).** Legacy components keep DESIGN.md section 9's breakpoints unchanged until each is individually migrated in its own S10.x sub-stage — the app is never in a state with two conflicting responsive systems on screen at once. The new shell's own navigation chrome (bottom nav/rail placement, destination layout pattern, touch-target sizing) uses the tiered, available-space specification in section 28.1 instead, generalizing the marker host's free-area/available-space approach rather than adopting the prototype's 690/1000px thresholds. **AC:** nothing in section 28.1 changes a DESIGN.md section 9 value; a legacy component under migration keeps passing its existing breakpoint-dependent tests until its own S10.x stage replaces it.

### 28.1 Responsive shell specification (U-03 approved; U-16 resolved) — architecture APPROVED 2026-11-22

**Principle:** three independent signals — width, height, pointer/hover capability — not device category. Legacy components (Map Configs, POI panel, Privacy panel, the current dock) keep DESIGN.md section 9's breakpoints completely unchanged until each is individually migrated in its own S10.x sub-stage (section 26); the app is never in a state with two conflicting responsive systems live on the same screen. The new shell's navigation chrome generalizes the marker host's already-proven `free-area.js` available-space approach — the nav bar/rail is itself treated as a "cover" subtracted from the free area, exactly as the side panel, dock and explorer already are (S5) — rather than adopting the prototype's 690px/1000px width-only thresholds.

**Tier 1 — Compact** (width ≤ 600px, any height, any pointer). Covers folded foldables (~344–412px), standard phones portrait (~360–430px). Bottom navigation bar; each destination single-pane, full-screen; contextual overlays are bottom sheets (today's host compact state). Short-height sub-case, height ≤ 420px (phone landscape): bottom nav collapses to icon-only, no labels, and is itself subtracted from the free-area calculation.

**Tier 2 — Expanded touch** (601–900px width, pointer: coarse). Covers unfolded foldables (~717–884px), 7–8" tablets portrait. Bottom navigation bar stays (still touch-primary); a destination with a natural list+detail split (Trips list+itinerary, Explore discover+detail) may show both panes side by side only if the free-area calculation says there's room, otherwise falls back to Tier 1's single-pane; contextual overlays become side panels when free-area has ≥320px left after the nav bar and open pane — reuses MD-06's "room, not device" rule verbatim, not a new threshold. Short-height sub-case as Tier 1 (≤420px height): nav collapses to icon-only.

**Tier 3 — Tablet / mid-width** (901–1200px). **U-16 decided 2026-11-22.** Split by hover capability, not just width, to avoid a contradiction between "touch-only" and a hybrid laptop in the same width band:
  - **`(hover: none) and (pointer: coarse)` — touch-only tablet (the U-16 case):** a **compact, touch-friendly left navigation rail** — icon-only, no forced text labels, no affordance that depends on `:hover` (no hover-reveal menus, no tooltip-only labelling; any label is either always visible or reachable via a tap-held/long-press disclosure, same pattern as the marker host's existing More menu). **Minimum 44px touch targets** (not the 40px fallback used elsewhere for a fine pointer). Short/landscape sub-case: at height ≤ 500px (a tablet rotated to a shallow landscape split-screen) the rail compresses further (reduced vertical padding between icons, same icon set) rather than hiding entries — content panes reflow to single-pane if free-area can't fit two, exactly as Tier 2 already falls back.
  - **Any other pointer/hover combination in this width band (e.g., a touch-capable laptop with a mouse/trackpad, `any-hover: hover`):** a labeled left rail (same as Tier 4's rail, scaled to the narrower width), hover states enabled, 40px targets.
  Two-pane destination layout is the default in both cases when free-area has room; single-pane fallback uses the same rule as Tier 2.

**Tier 4 — Desktop** (>1200px width). Left navigation rail with labels; multi-pane destinations; hover states enabled; touch sizing (44px) only if pointer:coarse is actually detected (touchscreen laptop/2-in-1) regardless of hover capability, standard 40px sizing otherwise.

**Cross-cutting rules at every tier:** recalculate on resize/orientation change (rotation-aware, as S5's recentring already is); reuse the host's existing `visualViewport`/keyboard-inset logic (80px minimum) for any new sheet/dialog at Tier 1/2, do not reimplement; no `vh`-only sizing for a new fixed/modal surface (DESIGN.md's 2026-11-14 note — `%`/`dvh`+`vh` fallback only); every touch target meets 44px wherever `(pointer: coarse)` is detected, independent of tier — this was already the cross-cutting intent, U-16 only makes it explicit and non-optional for Tier 3's touch-only case specifically.
