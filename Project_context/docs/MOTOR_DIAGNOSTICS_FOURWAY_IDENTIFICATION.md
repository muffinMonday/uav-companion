# Motor diagnostics: automatic ESC identification (read-only 4-way scan)

Status 2026-11-17: **implemented and synthetic-tested; NOT enabled for real hardware** (blocker in section 2). Owner decisions: identification is a default powered step; an unavailable identification is a warning plus acknowledgement when ordinary MSP control is proven restored; a restoration failure is a blocking safety fault; the manual ESC family selector and model/version field are removed. Authoritative backlog: `backlogs/in-progress/UAV_COMPANION_AUTOMATED_MOTOR_DIAGNOSTICS_BACKLOG.md`. Blackbox stays deferred.

## 1. Workflow (nine steps)
1 Connect the flight controller. 2 Read-only readiness checks. 3 Props-off and bench-safety checklist (zero-output initialization first). 4 Battery connected through the smoke stopper, powered-zero check. 5 **ESC identification** (4-way, read only). 6 Leave 4-way, restore MSP, repeat every safe-state check. 7 Confirm the motor layout, one-motor sweeps. 8 Stop verification, battery disconnection, recovery. 9 Result and optional save.
The scan runs only after the powered-zero check and before any nonzero output; it never runs while a motor turns. State machine: `POWERED_ZERO_VERIFICATION -> ESC_IDENTIFICATION -> POST_SCAN_RESTORE -> POWERED_ZERO_VERIFICATION (again) -> MOTOR_READY`.

## 2. Blocker for real hardware (why `VITE_BENCH_FOURWAY` is off for USB aircraft)
Primary-source reading (Betaflight tags 2025.12.5 and 4.5.2, `serial_4way.c`, `msp.c`, `drivers/motor.c`; 2026-11-17):
- `MSP_SET_PASSTHROUGH` (245, empty payload) enters 4-way; `esc4wayInit()` calls **`motorShutdown()`**, which stops the motor device and clears `motorDevice.initialized`, then `motorDisable()`. There is no armed check on entry.
- `esc4wayRelease()` (on `InterfaceExit`) only calls **`motorEnable()`**, which does nothing unless `initialized` is true. `initialized = true` is set only in `motorDevInit` at boot. By source reading, **on 2025.12.5 and 4.5.2 the motor outputs stay off after leaving 4-way until the flight controller reboots.** (`master` uses `motorDisable()` and `motorReinstateIo()`, so it re-enables.) Not hardware-tested.
- `DeviceInitFlash` forces each ESC into its bootloader. Whether `DeviceReset` returns the ESC to its application is **unverified**; without it an ESC stays in the bootloader until power-cycled.
- Consequence: after the scan there would be no DShot output and no fresh zero-RPM telemetry, so the restoration proof (section 4) cannot succeed and the session faults closed ("Disconnect the flight battery now."). A reboot would need `MSP_REBOOT`, which is prohibited, and drops the USB connection.
Owner rule applied: the 4-way functionality is **not enabled for real hardware**; the proof is not weakened. The build switch `VITE_BENCH_FOURWAY` (default off) is `1` (every transport), `synthetic` (only the simulated flight controller; used for the live isolated lab, so the screens can be checked) or anything else (the step does not exist). To enable it for hardware the owner needs one bench check on one ESC set: after `InterfaceExit` (and `DeviceReset`), does RPM telemetry come back without a reboot? Evidence needed: a trace with the scan, the stop proof and fresh zero-RPM telemetry on 2025.12.5, props removed, supervised. If motors do not come back, the options are a firmware that re-enables them (master-style) or a separate owner decision about a reboot-based design.

## 3. Read-only protocol boundary (`src/fourway/`)
Original code written from the protocol facts; Betaflight (GPL-3.0) and esc-configurator (AGPL-3.0) code is not copied (their text, comments and identifiers are not reused).
Frame: request `0x2F cmd addrH addrL len params.. crcH crcL`; response `0x2E cmd addrH addrL len params.. ack crcH crcL`; CRC-16/XMODEM over everything before the CRC bytes (the ACK included in responses); `len 0` means 256 (never sent).
| Command | Hex | Allowed | Why |
|---|---|---|---|
| TestAlive, ProtocolGetVersion (108), InterfaceGetName ("m4wFCIntf"), InterfaceGetVersion | 0x30 to 0x33 | yes | interface probe, no ESC write |
| InterfaceExit | 0x34 | yes | leaves 4-way |
| DeviceReset (channel, address 0 only) | 0x35 | yes, recovery attempt | restarts the ESC bootloader command; address 1 would hold the line low 300 ms and is refused; effect unverified (section 2) |
| DeviceInitFlash (channel) | 0x37 | yes | pokes the ESC into its bootloader to read it; not passive |
| DeviceRead (length 1..255, address 0..0xFFFE) | 0x3A | yes | bootloader address-set plus read; no write |
| EraseAll 0x38, PageErase 0x39, Write 0x3B, C2CK_LOW 0x3C, ReadEEprom 0x3D, WriteEEprom 0x3E, SetMode 0x3F, Verify 0x40, every other value | | **never** | `buildRequest` throws for all 248 non-allowlisted bytes |
Enter: MSP v1 `$M<` size 0 id 245 (`24 4D 3C 00 F5 F5`); the reply byte is the ESC count; from then the FC speaks only 4-way. `MSP_SET_PASSTHROUGH` is encodable only in `src/fourway/codec.js`. The only 4-way write site is `src/fourway/boundary.js` (one private method that calls `buildRequest`, then the raw transport write); the motor boundary refuses all sends while the controller's `fwBusy` is true, the poll loop and stop loops send nothing in 4-way mode, and the state machine grants no permission (not even a stop) in `ESC_IDENTIFICATION`. Static tests: `fourway-static-unit`, `bench-safety-unit`.
Identification reads (SiLabs BLB, modes 1): settings at 0x1A00 (0xE8B1, 0xE8B2) or 0x3000 (0xE8B5), 0x70 bytes: MAIN/SUB revision, layout string at 0x40, MCU string at 0x50, name at 0x60. ARM bootloader (mode 4, signature 0x1F06 at 0x7C00 or 0x3506 at 0xF800): file name 16 bytes at offset minus 32 and 0xB0 bytes at the offset; accepted as AM32 only when the boot character is 0x02, 0x14 or 0x06.
**Supported families:** BLHeli_S, Bluejay (SiLabs), AM32 (ARM). **Unsupported / displayed as unavailable, never guessed:** BLHeli_32 (not reliably distinguishable from other ARM-bootloader ESCs), Atmel BLHeli, KISS (STK500), anything with an unknown signature or blank settings. A reported target or layout is not necessarily the retail hardware model; the screens say "Firmware target", "Reported firmware" and "Retail model cannot be independently verified".

## 4. Restoration proof and failure policy
After every scan the controller proves, in this order: 4-way left and **MSP answers** (`MSP_API_VERSION`, 3 tries; this, not the 4-way exit reply, is the proof); FC identity re-read and equal (variant, firmware, API, board id, derived UID key); external 1000 sent repeatedly through the audited boundary with FC-side read-back 1000 on all four motors; fresh valid zero-RPM telemetry for 1 s; then the powered-zero check runs again (3 s, arming, DShot statistics) before motor choice. Any step failing within the limits faults closed.
- **Identification unavailable, MSP proven restored:** prominent plain-language warning naming the ESCs, explicit acknowledgement (`ESC_ACK`), then the normal checks; the result records the incomplete identification. The start interlock `esc-identification` refuses a nonzero run until the scan ran, the identity matched and any warning was acknowledged.
- **4-way exit or MSP restoration not proven:** `LOCKED_FAULT` (`fourway-exit-unproven`, `restore-incomplete`, `different-flight-controller-after-scan`), "Disconnect the flight battery now." first, no nonzero command, recovery marker retained, `transportAvailable` false where MSP is not proven, a fresh connection and full safe-state start required.
- **Stop & zero during the scan:** visible and one tap; it abandons the scan, leaves 4-way, then proves the stop. The control line says normal motor commands are unavailable during the scan; delivery is never claimed. Battery disconnection is the only cutoff that always works.

## 5. Eligibility and privacy
- The allowlist no longer matches on `escFamily` or `escModel` (removed from the UI, state, validation and records). `OWNER_APPROVED` keeps the one approved flight-controller combination and its stop-validation evidence; its former ESC description is kept only as `referenceEscFamily` and `referenceEscNote` (informational; never matched). Limitation: a different ESC set behind the same approved flight controller now matches. Compensation: the automatic scan, a visible warning when the reported family differs from `referenceEscFamily`, and the recorded observation. Nothing else was widened (variant, firmware, API, target, board id, protocol, evidence and the unlock all still apply).
- The raw `MSP_UID` is never in the view, a record or an export. `fcFingerprint` is the first 12 hex digits of SHA-256 over a label, the UID and the target name (null without SubtleCrypto): shown and saved only as a change-detection aid, not a hardware identity.
- Scanned ESC metadata is stored as `escObservation` (sanitized: whitelisted fields, clipped strings, no UID) in the saved record and the evidence export, only when the user presses Save. History grouping uses the flight-controller identity plus the fingerprint.

## 6. Hazard-analysis and fault-injection additions
H13 (4-way mode traps the FC): FC never leaves 4-way (exit no reply, bad CRC, never) -> `LOCKED_FAULT`, battery instruction. H14 (ESC left in bootloader / motors stay off after exit) -> no fresh zero RPM -> fault. H15 (command written in 4-way mode) -> hard gates, `mspWhileFourWay` empty in tests. H16 (mutating 4-way command) -> allowlist at encode time plus static tests. H17 (different board answers after the scan) -> identity re-read fault. Tests: `bench-fourway-unit` (success, partial, exit unproven x3, motors stay off, Stop & zero in scan, USB lost, different board, flag off), `fourway-boundary-unit`, `fourway-codec-unit`, `fourway-static-unit`, browser `fourway-ui`.
